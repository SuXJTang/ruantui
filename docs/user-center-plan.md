## 二、你提的两项

### 1. 改昵称 + 头像

**字段现成，工作量中等。**

| 要点 | 方案 |
|---|---|
| 昵称 | 2-16 字，不能重复（可选），支持中文 |
| 头像 | 两种方式：<br>A. 上传图片到 Supabase Storage（需要建 bucket）<br>B. 从预设图标里选一个（零存储，最省事） |
| 显示位置 | 用户中心卡片、账号菜单、可能的工具评论区 |

**我的建议：先做 B（预设头像），后续再考虑上传。**

理由：
- 用户上传头像要处理大小限制、格式校验、存储配额、内容审核
- 预设头像（20 个左右的图标/配色组合）视觉上更好看，零维护
- 真要做上传，Supabase 免费版 Storage 只有 1GB

### 2. 改密码

**Supabase Auth 原生支持，工作量小。**

```
流程：
  1. 输入当前密码（验证身份）
  2. 输入新密码
  3. 确认新密码
  4. 调 supabase.auth.updateUser({ password })
```

**注意**：改完密码后，当前 session 不会失效，但其他设备的 session 会。

## 三、你没提但应该做的

按重要程度排序：

### 🔴 必须做（不做会出问题）

#### 3.1 忘记密码 / 重置密码

**现在的致命缺陷**：用户密码忘了就**永久锁死**，只能找你手动改。

```
流程：
  登录框 → 「忘记密码？」→ 输入邮箱
  → Supabase 发重置邮件
  → 点邮件链接 → 设置新密码
```

**这比改密码更重要**，因为改密码需要先登录，忘密码则完全进不去。

#### 3.2 改密码后重新登录

改密码要让**其他设备掉线**，否则手机改了电脑还能用，不安全。

#### 3.3 删除账号

用户有权删除自己的账号（个人信息保护法要求）。

```
流程：
  用户中心 → 危险操作 → 删除账号
  → 输入密码确认 + 二次确认弹窗
  → 删除 profiles 行 + auth.users 行
```

**注意**：删 auth.users 需要 service_role 权限，前端拿不到。
方案：
- A. Worker 加一个 `/api/delete-account` 接口（要验证 JWT）
- B. 只标记 `deleted_at`，不真删（软删除）
- C. 让用户联系你手动删

**建议 B**：软删除，保留数据可恢复，符合实际。

### 🟡 应该做（体验明显更好）

#### 3.4 账号安全：登录设备管理

显示「该账号在哪些设备登录过」，可以踢掉陌生设备。

**Supabase 支持**：`auth.admin.signOut(userId)` 或用户自己 `signOut({scope:'others'})`。

#### 3.5 改邮箱

用户换邮箱（旧邮箱不用了）。

```
流程：
  输入新邮箱 → Supabase 发验证邮件到新邮箱
  → 点链接确认 → 生效
```

**注意**：Supabase 默认要求**同时验证新旧两个邮箱**，配置可以改。

#### 3.6 注销/停用而不是删除

「暂时不想用，但以后可能回来」—— 比删除温和。

### 🟢 可以加（锦上添花）

#### 3.7 注册时间 / 账号年龄

用户中心显示「加入于 2026-08-15」，增加归属感。

**字段现成**（`created_at`），前端加一行就行。

#### 3.8 我发布的评价（如果以后做评论功能）

现在没有评论功能，但如果工具卡允许用户评论，用户中心要有「我的评论」入口。

#### 3.9 邀请码 / 推荐奖励

VIP 用户邀请新用户送会员，是拉新手段。

**但你的站现在用户基数小，这个可以延后。**

#### 3.10 通知偏好设置

用户是否接收新工具上线通知、VIP 到期提醒等。

**现在公告是全局的，做偏好要改通知系统，成本较高，延后。**

#### 3.11 下载记录

用户下载过哪些工具，方便找回。

**现在有 `tool_downloads` 表但只记链接不记用户**，要加 `user_id` 字段。

## 五、我的具体方案

### 界面设计

用户中心顶部卡片右侧加一个「编辑」按钮：

```
┌─────────────────────────────────┐
│  (头像)  昵称  👑VIP      [编辑] │
│          邮箱                    │
│          👑 有效期至 xxx         │
└─────────────────────────────────┘
```

点「编辑」进入设置页：

```
┌─────────────────────────────────┐
│  ← 设置                          │
├─────────────────────────────────┤
│  个人资料                        │
│    头像    [当前头像] [更换]     │
│    昵称    [________] 保存       │
├─────────────────────────────────┤
│  账号安全                        │
│    修改密码            >         │
│    修改邮箱            >         │
│    退出所有设备        >         │
├─────────────────────────────────┤
│  其他                            │
│    加入时间  2026-08-15          │
│    我的收藏  12 个               │
├─────────────────────────────────┤
│  危险操作                        │
│    删除账号            >         │
└─────────────────────────────────┘
```

### 预设头像方案

20 个左右的组合，用户选一个：

```
方案 A：彩色圆底 + 首字母（最简单的，现在的样子，只是可换颜色）
方案 B：20 个图标（🐱 🐶 🦊 🐼 🐨 ...）+ 背景色
方案 C：纯色渐变背景（8 种配色）
```

**我推荐 B**：卡通头像对工具站友好，用户有选择感。

### 技术实现

**无需改表结构**（`nickname`、`avatar_url` 都有）。

```
nickname       → 存昵称文字
avatar_url     → 存预设头像的标识，如 "cat" 或 "emoji:🐱"
                  不用真 URL，就用短标识
```

需要新增的 RLS 策略（让用户能改自己的 profile）：

```sql
create policy "profiles_update_self" on profiles
  for update using (auth.uid() = id)
  with check (auth.uid() = id);
```

**注意**：这条要限制只能改 `nickname` 和 `avatar_url`，
不能改 `vip_until`（否则用户自己开通 VIP）。

现有触发器已经保护了 `vip_until`，但更稳妥的做法是加列级权限。

## 七、一个安全提醒

现在 `profiles` 表的 RLS：

```
profiles_select_admin  管理员能看到所有
（用户能看自己的吗？需要确认）
```

做「改自己资料」之前必须确认：
- 用户能 UPDATE 自己的行
- 用户**不能** UPDATE `vip_until`
- 用户**不能** UPDATE 别人的行

这三点任何一点缺失都是安全漏洞。
